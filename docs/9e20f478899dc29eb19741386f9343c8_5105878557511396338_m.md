# OpenList-Worker 深度安全审计报告

- **审计对象**：`https://github.com/WMZZwmzz/OpenList-Worker`（OpenListTeam/OpenList-Worker 的 fork）
- **审计提交**：fork HEAD（基于 upstream `82bd05d`，fork 额外约 20 个提交，含 `f1f6f46`/`af03d97`/`3f61372`/`42617ba` 等安全加固）
- **代码规模**：`src/backend` 约 10.8 万行、552 个文件、78 个存储驱动；另有 Cloudflare Workers / EdgeOne Functions / Vercel / ESA 边缘层
- **审计方式**：全量源码静态审计（fork 与 upstream diff、按域拆分）+ 关键发现逐条人工复核 + 依赖 SCA + CI/供应链检查
- **结论**：未发现可直接匿名利用的 Critical 漏洞。发现 **4 项高危、10 项中危、11 项低危**，主要集中在 **Alias 驱动的租户隔离**、**分享提取码爆破**、**SSRF 域名白名单**、**分享口令导致整库写锁死** 四处。多数基础设施级防护（路径归一化、逐跳 SSRF、字段加密、写前守卫、CI 固定 SHA）已做得较扎实，问题多为加固过程中的残余缺口。

> 说明：本文所有行号均对应审计时 fork HEAD。`src/` 下的路径均相对仓库根目录。

## 1. 高危问题（High）

### H-1 Alias 驱动丢失用户上下文，租户隔离与目录 ACL 失效

**位置**
- `src/backend/drivers/alias/driver.ts`（`list/get/mkdir/rename/remove/move/copy/put` 直接 import op 函数并以 `targetFullPath` 调用，未传 `StorageRequestContext`）
- `src/backend/internal/op/storage.ts:179-217`（`assertMetaWritable` / `assertWithinUserRoot` 首行均 `if (!user) return`）
- 源码注释已自认：“这**不能**替代 D-5（Alias 驱动…那些内部调用不带 requestContext）”。

**问题**
Alias 存储把虚拟路径映射为另一存储的全局物理路径后，自行调用 `listItems/getItem/putItem/...`。这些 op 函数的租户根校验（`isWithinUserRoot`）和目录 ACL（`meta.write_users` / `read_users`）都依赖 `requestContext.user`；Alias 调用不传上下文，于是两道闸直接短路。

**影响**
若管理员创建了 Alias 存储（常见于把多个存储拼成一个目录树），任何受限用户（`base_path=/alice`）可通过挂载在该前缀下的 Alias 读写**其根目录之外**的路径，并绕过目录级 `write_users/read_users` 名单。属于跨租户越权（读写）。

**利用条件与置信度**
需已配置 Alias 存储；无需管理员交互。源码注释明确确认，置信度高。

**修复建议**
- 给 `StorageDriver` 接口补充 `StorageRequestContext`（至少 `user`），Alias 透传；
- 或在 Alias 内部对 `targetFullPath` 显式执行 `isWithinUserRoot(user, ...)` 与 meta ACL 检查；
- 在 op 层对“无 user 的内部调用”改为显式 `internal: true` 白名单，避免默认放行。

### H-2 分享提取码在主接口可被无限爆破

**位置**
- `src/backend/internal/op/share.ts:107-167`：`resolveShare(reqPath, password, envCtx, clientKey?)`
- `src/backend/server/fs.ts:328`（`/fs/list`）、`447`（`/fs/get`）、`737`（`/fs/details`）均只传 3 个参数，**未传 `clientKey`**
- 对照 `src/backend/server/raw.ts:462-467` 的 `/sd` 直链**正确**传入了 `shareClientKey(c)`

**问题**
分享口令失败节流（`PWD_MAX_FAILS=8 / 10min`）只有在 `trustedSource = !!clientKey && clientKey !== "unknown"` 时才生效（`share.ts:155-167`）。`/fs/*` 三个主入口不传 `clientKey`，`trustedSource` 恒为 false，因此：
- 错误口令不计数、不锁定；
- 通过 `/api/fs/get` 可反复提交 `{ path: "/@s/<id>", password: "..." }`，并直接拿到文件内容。

**影响**
分享提取码通常为 4~6 位（用户自定义），匿名攻击者可在数分钟内穷举，进而下载受保护分享。`/fs` 路由也没有像 `/d /p /sd /dav /s3` 那样的全局限流。

**置信度**
高。代码路径明确，`raw.ts` 的正确用法可作为反证。

**修复建议**
所有 `resolveShare` 调用点统一传入 `shareClientKey(c)`；将失败计数改为跨实例共享（KV），并对 `/api/fs/*` 增加匿名限流。

### H-3 SSRF 白名单可被 `nip.io` 域名与 302 跳转绕过

**位置**
- `src/backend/pkg/http.ts:367-375`（`dnsRebindPatterns`）
- `src/backend/server/raw.ts:99-131`（`safeProxyFetch` 逐跳 `assertSafeUrl`）

**问题**
`isSafeUrl` 对 DNS 重绑定服务只拦截了字面 `(^|\.)127\.0\.0\.1\.nip\.io$`，而 `nip.io` 的规则是 `<任意 IP>.nip.io` 解析到该 IP。因此：
- `169.254.169.254.nip.io`（云元数据）
- `10.0.0.1.nip.io`、`192.168.1.1.nip.io`（内网）

均可通过校验，且 `isSafeUrl` **不做 DNS 解析后的 IP 判定**，存在 DNS rebinding 窗口。

`safeProxyFetch` 虽然逐跳校验，但每一跳仍调用同一个有缺陷的 `assertSafeUrl`——攻击者只需让上游返回 `302 Location: http://169.254.169.254.nip.io/latest/meta-data/`，即可把服务端请求引入元数据端点。

**影响**
读取云元数据/内网服务（AWS `169.254.169.254`、GCP、阿里云等），在 Workers/Serverless 场景可导致临时凭据泄露。触发面包括：驱动返回的 `raw_url`、`seed.ts` 的 `fetchSafe`、UrlTree 用户 URL、归档下载等。

**置信度**
高（代码路径明确）。利用需一个可控的上游 URL 或可返回 302 的第三方。

**修复建议**
- 对解析后的主机名做 DNS 解析并校验所有返回 IP（或改用平台提供的域名/IP 过滤能力）；
- 扩充重绑定域名黑名单：对任意 `<ip>.nip.io` / `<ip>.xip.io` 解析出的 IP 一律走内网判定；
- 对 `nip.io/xip.io/localtest.me` 等直接整体拒绝，或只允许显式 `SSRF_ALLOWED_HOSTS`。

### H-4 分享口令为 `enc:vN:` 形式时触发全库解密失败并永久禁止写回

**位置**
- `src/backend/server/share.ts:170`（`pwd: body.pwd || ""`，**无格式校验**）
- `src/backend/pkg/crypto.ts:523-551`（`^enc:v(\d+):` 且版本 1–6 即被认定为密文）
- `src/backend/internal/model/db.ts:1829-1835`（`sealValue` 对已带前缀的字符串**幂等跳过**）
- `src/backend/internal/model/db.ts:1919-1950`（`hasSealedValues` 覆盖 `shares[].pwd`）
- `src/backend/internal/model/db.ts:1273-1291` 与 `2279-2291`（解密失败 → `dbSealedReadUntrusted=true` → 所有 `saveDb` 被拒）

**问题**
任意拥有 `SHARE` 权限的用户创建一个口令为 `enc:v1:xxxx` 的分享即可：
1. `share.ts` 原样存入；
2. `saveDb` 封存阶段 `sealValue` 认为“已是密文”，不加密直接落盘；
3. 下次加载时按前缀解密，内容非法 → 解密失败；
4. `hasSealedValues(memoryDb)` 为真 → 标记库不可信 → **整库所有写入被永久拒绝**（除 `force`）。

**影响**
整站配置无法保存（登录、设置、存储、用户管理全部写入失败），且重启后仍复现，需人工改存储快照才能恢复。属于**持久的整站写锁死**。

**置信度**
高（逐行链路已验证）。

**修复建议**
- 在 `share.ts`（以及 `metas[].password`）写入前拒绝形如 `^enc:v\d+:` 的用户输入，或统一加转义前缀；
- 更稳妥：`sealValue` 不应仅凭前缀判定“已是密文”，应校验 base64/schema 与 MAC；解密失败时应“隔离单字段”而不是锁定整库写入。

## 2. 中危问题（Medium）

### M-1 Emby 管理员 API Key 通过 302 直链泄露
`src/backend/drivers/emby/driver.ts:173` 把 `api_key=<管理员 token>` 拼进 `raw_url`；`emby` 不在 `DRIVER_FORCE_PROXY`/`DRIVER_PREFER_PROXY`（`internal/driver/proxy.ts:112-143`），因此 `/d` 走 302（`server/raw.ts:650`）。任何有读权限者（或公开分享的游客）在 `Location`、浏览器历史、Referer、CDN 日志中即可拿到该 Key，可完全控制 Emby。
**修复**：将 `emby` 加入强制代理，或在服务端代理取流，绝不把凭据放入 `raw_url`。

### M-2 遗留无盐单层 SHA-256 仍被接受（pass-the-hash）
`src/backend/server/auth.ts:342-359`：注释称“遗留格式不再支持”，但代码在 `!user.salt` 时执行 `constantTimeEqualHex(stored, input)`，即直接接受前端提交的静态哈希。拿到单个用户哈希（备份/泄露）即可在无需知道明文的情况下登录该账号，且 `STATIC_HASH_SALT` 为公开常量。
**修复**：删除 357-358 的单层分支，仅保留 HMAC 加盐双层校验；或强制一次性迁移。

### M-3 `otp_pending` 令牌可通过 `checkAdminAuth`
`src/backend/pkg/utils.ts:30-76` 的管理员判定只做 JWT 验签、`jwtClaimsAcceptable`、jti、库中用户存在/未禁用、密码指纹、`user.role===ADMIN`，**未调用 `isOtpPendingPayload`**（`permission.ts:21-26` 的 claim 校验也不含 `type`）。`issueOtpPendingToken`（`auth.ts:667-682`）不带 `role`，但 `checkAdminAuth` 取库中角色，因此对 `pwd_update_at` 为空、`token_epoch` 为 0 的**遗留管理员**，一个仅在 SSO/WebAuthn 第一因子后签发的 5 分钟待兑换令牌即可访问 `/api/admin/*`，绕过 TOTP。
**修复**：`jwtClaimsAcceptable` 统一拒绝 `type==="otp_pending"`；`checkAdminAuth` 复用 `authUserFromReq` 的身份解析。

### M-4 静态加密密钥与密文同存储，且复用为 JWT 密钥
`db.ts:1446` 将自动密钥写入 `openlist_encryption_secret`（与被加密的库同一持久化后端）；`middlewares.ts:143-170` 又把同一把密钥作为 JWT 签名密钥回退。能读取 KV/D1/MySQL/备份的人可同时解密全部 `refresh_token`/OTP 种子/密码哈希**并伪造任意管理员 JWT**，突破了“静态加密”对存储管理员的隔离假设。
**修复**：加密密钥与 JWT 密钥分离，且要求通过环境变量/Secret 注入；不要在库同一存储中持久化密钥（或至少用平台 Secret 包裹）。

### M-5 WebDAV PUT 无请求体上限
`src/backend/server/webdav.ts:391-400`：`Buffer.from(await c.req.arrayBuffer())` 先整体读入内存再落盘，没有 `MAX_UPLOAD`/`body_limit`/流式处理。拥有 `WEBDAV_MANAGE` 的用户可发送超大请求打爆 Worker/Node 内存。
**修复**：复用 `body_limit` 中间件，或改为流式读取并在累计超限时中止。

### M-6 解压总量预算可被伪造绕过
`src/backend/server/fs.ts:2278-2345` 的 `totalBytes` 累加的是中央目录里的 `entry.size`（攻击者可控），而 `extractZipEntry` 只对**单条目**限 64 MiB（`archive/zip.ts:31,112-172`）。伪造 `size=0` 的 10000 个条目可让每个条目实际解压 64 MiB，造成 CPU/内存/存储耗尽。
**修复**：以解压后的实际字节数累计总预算，而不是声明大小；并降低单条目/总条目上限。

### M-7 KV 代理未校验令牌吊销/版本/禁用状态
`functions/_kv-proxy.js:223-247`：用户通道仅验签 HS256 + `exp/nbf` + `Number(payload.role)===2`，不查 `jti` 黑名单、`token_epoch`、库中用户是否被禁用。管理员“退出登录”或“降权”后，旧 JWT 在有效期内仍可读写 KV（数据面），与主站 `checkAdminAuth` 的语义不一致。
**修复**：在边缘侧校验 `token_epoch`/`jti`（可通过已经代理的 KV 读取吊销名单），或缩短管理端 JWT 有效期并对写操作二次校验。

### M-8 阿里云盘 refresh_token 经 GET query 发往第三方中转
`drivers/aliyundrive_open/util.ts:122-129`：把 `refresh_token` 放进 URL query 请求 `api.oplist.org` / `api.alist.nn.ci`。查询串会进入各级代理/CDN/访问日志；恶意或失陷的中转可直接接管管理员阿里云账号。虽然 `api_url_address` 过了 SSRF 校验，但信任边界未被声明。
**修复**：改为 POST body 传输；第三方中转改为显式 opt-in + 运营方白名单。

### M-9 共享驱动实例的 token 刷新竞态
`internal/op/storage.ts` 按 `${storage.id}_${storage.modified}` 缓存驱动实例，但 `guangyapan/util.ts:132-153`、`115open/util.ts:115-150`、`aliyundrive_open/util.ts:245-247` 的 401 刷新没有单飞锁。并发请求会各自动用 refresh token，而多数平台会轮换令牌，导致失败方持久化旧 token，存储持续不可用。
**修复**：按 storage 加单飞/互斥，仅持久化最新刷新结果。

### M-10 UrlTree HEAD 重定向 SSRF
`drivers/url_tree/driver.ts:172-182`：`assertSafeUrl(url)` 只校验首跳，随后 `fetch(url,{method:"HEAD"})` 默认跟随 302。可写 UrlTree 的用户（含游客，若开启可写）可让 URL 跳转至 `169.254.169.254` 或内网。
**修复**：`redirect:"manual"` 并逐跳校验（复用 `safeProxyFetch`），或禁止重定向。

## 4. 已确认做得较好的加固（避免重复报告）

以下机制经源码核对确实存在且实现正确，审计中未再作为漏洞上报：

1. **路径归一化**：`decodePathFully` + `collapsePathSegments` + `canonicalVirtualPath` 同源；`base_path` 钳制、`/@s` 分享命名空间钳制（`permission.ts:145-273`）。
2. **重定向 SSRF**：`safeProxyFetch` 手动逐跳校验并在跨域时剥离 Cookie/Authorization（`raw.ts:86-132`）。
3. **归档 zip-slip**：`safeArchiveEntryPath` + `isWithinUserRoot` 双重校验；条目数/归档体积上限。
4. **认证**：JWT alg 固定 HS256、`iss/aud` 校验、jti 吊销、`token_epoch`、`pwd_update_at`、2FA 待兑换令牌在 `authUserFromReq` 中被显式拒绝；空口令拒绝。
5. **字段加密**：`enc:v1..v6` 前缀驱动、HKDF/PBKDF2、HMAC、弱密钥告警；`hasSealedValues` 写前守卫防止半成品落盘。
6. **CI/供应链**：workflow 的 action 全部按完整 SHA 固定、`permissions: contents: read`、Gitee SSH key 走 env；`scripts/fetch-frontend.mjs` 做 SHA 固定、SRI/摘要校验、ref/URL 白名单、`ALLOW_UNVERIFIED` 显式降级。
7. **上传/文件名**：`validateFileName` 拒绝 CR/LF 与路径分隔符；S3/R2 驱动层拒绝 `..`/`/`。

**依赖 SCA（OSV）**：459 个包中，命中的已知漏洞包均不在后端运行时路径——`axios 1.19.0` 未被后端引用；`dompurify/mermaid/katex/handlebars/undici/ws/@fastify/busboy` 属前端或开发依赖；`zod 3.22.3` 为仅开发传递依赖（生产为 3.25.76）。**未发现可通过后端触达的已知依赖漏洞**。
